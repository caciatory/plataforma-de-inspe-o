Atualizado: 2026-08-05. Baseado em `docs/especificacao-tecnica-v1.md` §5 (9 fases) e no estado real do código (branches, migrations) nesta data.

Cada passo abaixo é uma unidade fechada: você cola o prompt sugerido, o processo documentado em `docs/PROCESSO.md` (`brainstorming` → `writing-plans` → `subagent-driven-development`) roda até o fim, e o passo só é considerado pronto quando passar pelas 3 skills de fechamento (seção final deste doc). Só então vá para o próximo prompt da lista.

**Regra deste documento:** ao final de cada fase concluída, este roadmap é atualizado com um resumo simples do que foi feito (seção "Progresso" abaixo) e, se algo descoberto durante a task justificar, uma nova fase é sugerida/inserida na lista.

## Fase 4 — Pontuação ✅ concluída (2026-08-05)

RF-38 a RF-42, RNF-18–19. O bloqueio original (valores de corte A/B/C e fórmula de pontuação indefinidos, §6 da especificação) tinha uma causa mais profunda: o texto de RF-38 a RF-42 ainda assumia a classificação fixa de 4 valores (ótimo/médio/ruim/NF) de antes da Fase 2.8, que deixou de existir quando o schema generalizou pra ~22 `conjuntos_opcao` compartilhados (2 a 5 opções cada) mais os tipos `medição`/`texto`/`data`, nenhum dos quais tem classificação de qualidade embutida. Resolvida via `brainstorming` → `writing-plans` → `subagent-driven-development` (4 tasks). **Decisões fechadas no brainstorming:** fórmula de pontuação por posição — a opção na posição *i* entre N opções válidas (não-N.A.) pontua `10 - (i-1) × 8/(N-1)`, reproduzindo exatamente o 10/6/2 do RF-38 original pra conjuntos de 3 opções e interpolando pra qualquer N; medição reaproveita o resultado ok/atenção/crítico que a Peça 1a já calcula (`medicoes_resultado`), mapeado pra essa mesma escala 10/6/2; texto/data nunca pontuam; itens N.A. e pendentes ficam de fora das médias, mesmo princípio de exclusão que o antigo "NF"; cortes de classificação A≥8/B≥5/C<5; escopo é só cálculo — sem tela nova, a Fase 5 é quem vai consumir essas views depois. Coluna nova `opcoes.is_na boolean` (migration `00041`) vira a fonte estruturada de verdade pra quais opções são N.A., substituindo (só pra pontuação — o cliente continua usando a regex) a inferência por regex que já existia em `lib/checklist/siblings.ts`; backfilada com o mesmo padrão do regex, batendo exatamente nas 6 opções N.A. reais do seed. Três views novas, todas `security_invoker = true`: `checklist_item_score` (migration `00042`, ponto por resposta individual, fórmula por posição via CTE), `checklist_group_score` e `inspection_score` (migration `00043`, agregação por grupo e por inspeção com os cortes A/B/C). Simplificação deliberada em relação ao design doc: grupos/inspeções sem nenhuma resposta simplesmente não geram linha na view (em vez de uma linha com campos nulos) — comportamento idêntico pra qualquer chamador via `.maybeSingle()`/LEFT JOIN, documentado inline na própria migration `00043`. Este ambiente não tem acesso à base de dados ao vivo, então toda migration foi verificada por revisão estática de SQL (rastreamento manual, não execução) em vez de rodar teste automatizado — mas cada migration e arquivo de teste foi depois aplicado manualmente e confirmado pelo usuário direto na base real via SQL Editor do Supabase, incluindo conferência contra dados reais (não sintéticos): `checklist_item_score` validado contra 20 itens respondidos de verdade (10/6/2 em conjuntos de 3 opções, 7.33 interpolado num conjunto de 4 opções, null num item com opção N.A. selecionada) e `inspection_score` validado contra inspeções reais (notas 6–8 classificadas 'B' em inspeções que o usuário de fato preencheu, null/null em rascunhos ainda não tocados) — tudo correto. Duas rodadas de `requesting-code-review` ao longo do caminho (Task 3 precisou de um fixture pra cobrir exatamente a fronteira 5.0 B/C e uma nota de doc sobre a simplificação de escopo) — ambas resolvidas sem achado pendente. Design: `docs/superpowers/specs/2026-08-04-pontuacao-design.md`, plano: `docs/superpowers/plans/2026-08-04-pontuacao.md`.

## Regra de transição entre passos (o que mantém o processo seguro)

Ao final de cada fase, depois que `subagent-driven-development` terminar todas as tasks:

1. `superpowers:requesting-code-review` no branch inteiro — sempre.
2. `ponytail:ponytail-review` — só se a fase adicionou código/abstração nova (pula em passos de housekeeping/docs).
3. `security-review` — só se a fase tocar auth, RLS ou controle de acesso (ex.: Fase 5 admin, Fase 7 acesso do cliente).
4. `verify` — só se a fase tiver UI (dirige a feature de ponta a ponta no navegador, não só testes/typecheck).
5. `superpowers:verification-before-completion` antes de qualquer alegação de "pronto" — sempre.
6. `superpowers:finishing-a-development-branch` pra decidir merge/PR — sempre.

Só depois disso cole o prompt da próxima fase da lista.
